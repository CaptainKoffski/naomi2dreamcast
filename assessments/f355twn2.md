## Gate

```
f355twn2 PARKED G1 broken: no-render-after-handoff
```

**G1 broken — Flycast's Naomi multiboard shared-memory setup fails on this macOS
environment.** F355 is a multi-board game (master + slave video boards); Flycast
emulates it with cooperating processes sharing mapped memory. The battery run got
deep into loading, then stopped at video init (`evidence/f355twn2/raw/stdout.log`;
raw dirs are regenerable scratch, rotated by the next battery run):

```
hw/naomi/multiboard.cpp:391 E[NAOMI]: Can't open mapped file /naomi_multiboard_mem1: errno 2
ui/gui.cpp:1358 E[BOOT]: Cannot initialize Naomi multiboard shared memory
Flycast has stopped
```

**Vanilla control test (2026-08-11, controller-run): identical failure — not our
instrumentation, not the dump.** Stock Flycast 2.6 (`/Applications/Flycast.app`),
plain launch of the same `naomi/f355twn2.zip`: the master spawns a slave process,
the slave logs `multiboard.cpp:188 Time out waiting for multiboard vsync. Slave 0`,
then the same `naomi_multiboard_mem1: errno 2` / "Flycast has stopped". Per the
control-test rule this isolates the failure to the emulator/platform: F355 requires
Flycast's multi-process multiboard emulation, whose shared-memory setup fails on
this macOS environment in both vanilla and fork.

**Measured before the stop (lower-bound context only — unrepresentative, no render):**
ARAM fully loaded, peak 8,323,024 (content_total 7,923,189) · main DMA high-water
29,332,992 (already 1.75× the DC's 16 MB — a real porting signal if it holds up
under a working capture) · streaming 7,510 DMA events, 217,416,192 B total /
67,717,664 B unique, re-read ratio 0.6885, steady 18.5 MB/min. VRAM: all zeros
(the stop is at video init).

**What would unblock:** Flycast's multiboard shared memory working on macOS
(fix or workaround for the `/naomi_multiboard_mem1` shm open), or measuring on
another platform where the multi-process multiboard path works.
