### Display blindness

All 10 battery screenshots show the same frozen NAOMI GD-ROM SYSTEM splash. That is a
**stale TA frame** left in the GL display path (kb §4.m class, same as `kurucham`), not
a hang: underneath it the game verifiably runs — BIOS handoff at 30.0 s, 3,200 GD DMA
events / 80,242,688 B streamed across the window, the full 8 MiB ARAM bank written, and
2,751,329 B of nonzero VRAM asset uploads (`memory.vram.nz_total`). This title
CPU-writes its frames, which the TA screenshot path never sees. The user watching the
live capture saw the same static splash — that was the stale TA frame the fork displays,
not what the game was doing.

Earlier battery runs falsely parked `ss2005` G1 **twice**: 6 consecutive healthy legs
were killed by a wrong boot-marker grep — "Initializing Naomi EEPROM" is logged only on
a game's first-ever boot, so its absence is not a hang signal (kb §4.n, fixed in
`f5bf2c4`; `eeprom_seen()` now greps the unconditional "monitor orientation" line).

Screenshots kept (first + last, identical splash, proving the freeze):

- `assessments/evidence/ss2005/shot-608s.png` — same splash at t=608 s, unchanged

## Gate

**G3 memory: aram peak > 2x DC capacity.** `memory.aram.peak = 8,388,608 B` (exactly
8 MiB, the full Naomi ARAM bank) against the DC's 2,097,152 B AICA RAM → utilization
4.00×, past `region_score()`'s `u > 2.0` gate; `nz_above_cap = 6,291,456 B` nonzero
above the cap at scan. Boot-time full-bank load — third in the campaign tally after
`ikaruga` (calibration) and `azumanga` (kb §6 item 1 checkpoint data point).

Evidence: `assessments/ss2005.metrics.json` → `memory.aram`; `guts.sdk_strings` names
the standard Sega/CRI sound stack doing the bank load (`sd2 for DC Ver 2.50.17`,
`mwSb`, `MANATEE.DRV`, CRI ADX/Sofdec) — the same driver family whose banks the official
Ikaruga DC port trimmed 4× to fit 2 MiB (kb §4.d precedent).

What would unblock it: a per-title audio trim (downsample the PCM banks / ADPCM) —
standard porting work with released-port precedent. But the gate is not the only memory
problem: main-RAM DMA high-water is `27,511,008 B` (1.64× the DC's 16 MB) and VRAM peak
`11,476,544 B` (1.37× the 8 MB cap), so this title needs reduction in all three regions.
VRAM is milder than the peak implies: nonzero content is only `2,751,329 B` total, with
`2,750,429 B` of it above the 8 MB line — an address-extent artifact of a
CPU-uploaded asset store parked high (the `kurucham` pattern); a port would relocate it.

Context values quoted from the sidecar (no axis scores exist — the pipeline stops at the
gate): streaming 3,200 DMA events, 80,242,688 B total / 32,032,768 B unique, re-read
ratio 0.6008, steady-state 7.316 MB/min (`short_window: false`); guts 1,048,576 B code,
2,568 functions, MMIO refs scif 2 / rtc 3 / g2ext 52, flags
`eeprom_bios`/`serial`/`rtc`; similarity inputs `developer_match: false`,
`sdk_overlap: "partial"` (Kunoichi2 2.07 / Ninja2 / `syStartCwKn` / AIPKN, KAMUI2, CRI —
all Mar-2001-era Katana-adjacent builds), `cart_loader_match: true`.

## Risks & notes

- **Display-path gap blocks emulator validation.** Even a ported build could not be
  visually validated in this emulator today — the fork shows a stale TA frame while the
  game CPU-writes its frames elsewhere. Per the working-style rule, rendering must be
  verified on real DC hardware; the emulator-side diagnostic is the raw-VRAM decode
  recipe (`FLYCAST_VRAMDUMP` + `vramdump2png.py`, kb §4.m).
- **All three memory regions over cap** (ARAM 4.00×, main 1.64×, VRAM 1.37×) — yet the
  game shipped on a 2004 PS2 CD, so the content demonstrably fits console-class budgets;
  the Naomi build simply loads full banks. A port is trim-everything work, not
  impossible-fit work.
- **Controls are the easy axis**: `controls.device_class = stick`. The game's own INPUT
  TEST menu (in-binary, `guts.sdk_strings`) lists UP/DOWN/RIGHT/LEFT + SELECT/CANCEL/
  HELP + START — one 8-way stick and three game buttons, 1:1 on a DC pad. Sources: MAME
  src/mame/sega/naomi.cpp @59e7c0b INPUT_PORTS `naomi`;
  [arcadeitalia ss2005](http://adb.arcadeitalia.net/dettaglio_mame.php?game_name=ss2005)
  and [ss2005o](http://adb.arcadeitalia.net/dettaglio_mame.php?game_name=ss2005o)
  (8-way joystick + 6-button JVS standard declaration, 2P solo). The
  [LaunchBox](https://gamesdb.launchbox-app.com/games/details/39342-super-shanghai-2005)
  claim of a "dual-analog control scheme" describes the PS2 pad layout — the binary's
  own `ANALOG STICK` / `DIRECTIONAL BUTTON` strings are PS2-origin leftovers — and is
  discounted for the cabinet.
- Main watermark `32,505,920 B` (informational, stale-data-prone) is 1.18× the DMA
  high-water — and byte-identical to `kurucham`'s main watermark, which smells like a
  content-scan ceiling artifact rather than real per-title content; treat with suspicion.
- MAME emulation status for the set is preliminary / imperfect graphics + sound
  (arcadeitalia, mirroring MAME `GAME_FLAGS`) — consistent with a title that trips
  emulator display paths, as observed here.
- Main-RAM v1 limitation carried from the spec: DMA high-water misses CPU-written data
  above the last DMA'd asset.
